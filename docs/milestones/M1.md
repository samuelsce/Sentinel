# M1 — ambiente e contratos

Entrega implementada em 8 de outubro de 2026. Esta etapa fornece a base reproduzível do Sentinel; o monitoramento de aplicações começa com ingestão e detecção nos marcos M3/M4.

## Resultado demonstrável

O Docker Compose inicia PostgreSQL, aplica migrations e sobe uma API Fastify, um worker Python privado e um frontend Next.js. A página consulta a API e mostra a conexão real com o banco. Não há métricas de segurança fictícias nem endpoint de ingestão sem autenticação.

O contrato v1 possui cinco tipos de evento, campos e metadata limitados por allowlists, lote de até 100 eventos e exemplos compartilhados. Zod gera JSON Schema Draft 2020-12; os mesmos 25 cenários são verificados por Zod, Ajv e Python. Limites de transporte e elegibilidade temporal também estão definidos, mas serão aplicados ao endpoint na M3.

As migrations criam usuários, organizações, vínculos, projetos, chaves, eventos e jobs. Relações compostas impedem referências incoerentes entre organizações, projetos, chaves e ambientes. Isso verifica integridade no banco; autorização de usuários pela API será implementada na M2.

## Evidências locais

Validação realizada no Windows com Node.js 24.20.0, Python 3.12.14 e containers Linux no Docker Desktop. PostgreSQL real: 18.6.

| Verificação | Resultado | Reprodução |
| --- | --- | --- |
| Lint e typecheck TypeScript | Passou | `pnpm check` |
| Testes TypeScript | 35 testes passaram, em dois arquivos | `pnpm test` |
| Contratos gerados | Sem divergência da fonte Zod | `pnpm contracts:check` |
| Lint e formato Python | Passou | `uv run --no-sync ruff check .` e `uv run --no-sync ruff format --check .` no detector |
| Testes Python | 31 testes passaram | `uv run --no-sync pytest -q` no detector |
| Build dos pacotes e frontend | Passou | `pnpm build` |
| Banco e migrations | Aplicação inicial e reaplicação passaram | `pnpm db:migrate` e `pnpm test:database` |
| Integridade entre escopos | Referências inválidas, duplicados e jobs inválidos foram rejeitados | `pnpm test:database` |
| Permissões de serviço | API e detector sem superuser/bypass de RLS; detector não lê usuários nem altera eventos | `pnpm test:database` |
| Ambiente completo | Imagens construídas, migration saiu com 0 e serviços ficaram saudáveis | Comandos do [README](../../README.md) |
| Comunicação web/API/banco | Liveness, readiness e conteúdo renderizado passaram | `pnpm test:smoke` |
| Falha de dependência | API viva com readiness 503 e página indicando conexão indisponível; recuperação verificada | Parar PostgreSQL e executar `pnpm test:smoke -- --expect-unavailable`; iniciar PostgreSQL e repetir o smoke normal |
| Desenvolvimento local | API/frontend com recarga local e conexão real passaram | Sequência de desenvolvimento do [README](../../README.md) |
| Inspeção visual | Tela em desktop e viewport de 390 × 844, sem rolagem horizontal | Navegador com serviços em modo de desenvolvimento |

Os testes de logs usam credenciais fictícias em query, headers, cookies e body e verificam que elas não são registradas. Testes de erro também verificam que exceções contendo URLs de banco não são devolvidas nem impressas.

Os 35 testes TypeScript e 31 Python incluem verificações dos mesmos casos de contrato; esses números não representam 66 cenários de produto distintos. Não constituem ainda a validação completa V01–V12 do MVP.

## CI e documentação

O [workflow da M1](../../.github/workflows/ci.yml) executa três jobs: TypeScript/build/contratos, Python/fixtures e Compose/PostgreSQL. As execuções e seus resultados públicos estão em [GitHub Actions](https://github.com/samuelsce/Sentinel/actions/workflows/ci.yml). A validação local acima é independente do resultado de cada execução da CI.

O [README](../../README.md) distingue funcionalidades implementadas das planejadas e fornece o caminho de avaliação para recrutadores. [DEVELOPMENT.md](../DEVELOPMENT.md) registra versões, configuração, permissões, migrations e recuperação. [CONTRACTS.md](../CONTRACTS.md) descreve o formato de eventos. [DESIGN.md](../DESIGN.md) registra a skill e a referência visual utilizada na tela inicial.

## Limites e próxima entrega

Esta etapa não implementa login/sessões, autorização por papel, emissão de chaves, ingestão, SDK, detecções, alertas ou investigação. O worker verifica suas dependências e aguarda; não consome jobs. As imagens são de desenvolvimento e as portas ficam restritas ao host local.

M2 implementará identidade e credenciais com sessões revogáveis, proteção CSRF, autorização por papel e isolamento de organizações na API. O dashboard completo e sua pesquisa visual estão previstos na M5.
